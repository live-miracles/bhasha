① The Cloudflare components & their isolation scope

Isolation scope is the whole game. Durable Objects are per-program (so one program can't touch another). D1 is one global, single-threaded database shared by every program — that single fact is the root of every bottleneck below.

② The media path — where the audio actually flows (this never touches D1)

Critically: audio delivery is fully insulated from D1. The listener pulls the relay's stable track from the SFU over WebRTC. The StreamRelay DO sits between the translator and the SFU precisely so a translator reconnect never changes the track listeners pull (no glitch, no re-pull). The 5k/50k bottlenecks are all in the control plane, not here.

Verified: partytracksListenerClient.pull() subscribes to {location:"remote", sessionId, trackName} on the SFU; StreamRelay.handleAttach pulls the translator track to /in and rebuildIngest republishes via /out; alarm()/pacingStep injects silence after 1.5 s gaps. The relay↔SFU WebSockets are internal — the listener only ever does a WebRTC pull from the SFU.

④ The bottlenecks — and exactly why

One root: the control plane uses a single, global, single-threaded D1 for hot, per-connection live state. Cloudflare docs: a D1 database is single-threaded, sequential — ~1,000 queries/s at 1 ms each; exceed it and queries queue, then return overloaded (our database_error).

B1 · D1 is global & single-threaded root

Every program's listener writes and admin reads share one sequential database. There is no horizontal write path.
CF docs: single-threaded, sequential; ~1k q/s @1ms; overloaded beyond capacity.

B2 · /request fails-closed

The audio join blocks on a D1 INSERT that audio delivery never reads. A saturated D1 → no connectionId → no audio.
Run #24: request 201 succeeded only 20% during the 90s burst (✓9,753 / ✗39,031).

B3 · live count = COUNT(*) scan

Admin count + report do COUNT(*)/GROUP BY over the table — a read that scales with rows, not listeners, and gets worse as the table grows mid-event.
Run #24 CF metrics: ~1,000,000 rows read / minute during the burst (vs ~350 baseline).

B4 · per-heartbeat D1 write

Each listener writes D1 every 90 s. The sustained write rate scales linearly with audience.
50k ÷ 90 s ≈ 556 writes/s > a single D1's ~333 single-row writes/s ceiling.

B5 · /active-publisher read on the hot path

Every join awaits a D1 read for relay coords that are static for a live program — needless contention during the join storm.
Awaited, blocks audio; 5k simultaneous joins = 5k redundant reads of unchanging data.

B6 · cross-program starvation

Because D1 is shared, one busy program's storm queues behind another program's admin reads. Blast radius = all programs.
Run #24: admin returned database_error + 17–64 s latencies during the burst.

⑤ How the proposed architecture resolves each

Principle: D1 is a reporting store, not a live-state store. Live per-connection state moves to the per-program Durable Object (in-memory, O(1), isolated); D1 receives a batched write-behind trickle and serves admin reads from a replica.

⑥ New chokepoints the design creates — and how it absorbs them

Moving live state to the DO replaces D1's chokepoint with the DO's. We design for that explicitly — every item below is surfaced in the plan with a mitigation, not discovered in production.

N1 · ProgramPresence DO becomes the funnel capacity

One per-program DO now takes every join/heartbeat/leave/snapshot. Cloudflare documents a soft ~1,000 req/s per individual DO; 50k → ~556 heartbeat ops/s + joins + snapshots leaves thin headroom.
Mitigation: within-program hash sharding — hash(connectionId)%N sub-DOs, snapshot = fan-in sum. Pre-built; enabled at sustained ~700–800 ops/s, any overload, or p95 drift.

N2 · per-mutate storage.transaction the trap

The existing DO writes the whole records map to storage on every call. Wiring heartbeats naively = 556 serialized storage transactions/s through one single-threaded actor — D1's problem, relocated.
Mitigation: mutate in-memory; persist on an alarm() cadence (2–5 s) + on eviction. Bounded checkpoint rate, not per-RPC.

N3 · stale window vs heartbeat correctness

staleAfterMs = 30s today, but the client heartbeats every 90s — wiring as-is would evict live listeners → massive under-count.
Mitigation: widen to ≥ 2× heartbeat (≥180s, aligned to the 240s active window); single source of truth for the constant.

N4 · Queue limits + at-least-once analytics

Cloudflare Queues: batch ≤100, ≤5,000 msg/s per queue, at-least-once (duplicates expected).
Mitigation: one multi-row UPSERT per batch (not 100 singles); idempotent on connectionId; dead-letter + retry defined. Join rate at 50k (arrivals over minutes) ≪ 5k/s.

N5 · DO alarm semantics durability

DO alarms run one-at-a-time with finite retries; a thrown alarm can drop the prune/checkpoint.
Mitigation: alarm handler catches + reschedules + is restart/eviction-safe (mirrors the proven relay self-heal alarm).

N6 · write-behind still one primary residual

Batched analytics still land on one D1 primary; read replication doesn't help writes.
Mitigation: batching cuts write-queries ~100×; per-program D1 (Phase 4) is the pre-scoped escape hatch if a single primary ever strains.

N7 · count cutover risk rollout

Switching the count source could show a wrong number mid-rollout — unacceptable for a live operator view.
Mitigation: dual-read — compute DO snapshot + COUNT(*), serve DO, log divergence, flip only after it proves accurate under load; instant rollback.

N8 · browser-close without /leave normal path

Most listeners just close the tab — /leave never fires. If TTL expiry is treated as an exception, counts drift high.
Mitigation: TTL expiry (the stale prune) is the primary disconnect path, observable and tested — not a fallback.
